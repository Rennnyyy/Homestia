# Frontend Is a Thin Consumer of the Aletheia Frontend Packages

**Status**: accepted
**Type**: decision
**Supersedes**: none

## Statement
The Homestia Angular app consumes the published `@rennnyyy/aletheia-tokens`, `-core` and `-ui` packages for every piece of platform behaviour: HTTP access, model loading, entity sync, SHACL validation, shape fetching, i18n helpers, theme/skin switching, entity table, entity form, entity reference select, object upload, confirm dialog, validation summary, buttons and cards. Homestia keeps only what is app-specific: the two entity pages (with their stage wizard and create wizard), the AI assistant panel and wizard, the accent palette axis, the bespoke header/sidebar chrome, the local Accordion primitive and the i18n dictionaries. Vendored copies of platform behaviour are not permitted; where a name must be preserved for call sites, it is a re-export shim — never a fork. The `aletheia-shell` package is **not** a dependency: the shell vocabulary the app actually uses lives in `-ui`. ^statement

## Rationale
The platform packages now carry the components and services that were previously vendored from a pre-extraction snapshot, so keeping local copies would mean maintaining two implementations of the same behaviour and drifting from every SDK fix. The token-driven skin registry (`provideSkins`) makes it possible for Homestia to keep its own visual identity while still consuming the SDK's theming machinery, and the CLI generates the entity surface from introspection so no hand-written model code remains. A thin app is also the only way the stricter SDK test criteria can be met without duplicating the SDK's own test effort. ^rationale

## Consequences
- The pages import `AletheiaHttpClient`, the wire types and `ShaclValidatorService` straight from `@rennnyyy/aletheia-core`; no re-export shim layer exists.
- `core/shapes/shape.model.ts` holds only Homestia's own shape IRIs; the shape engine and its types come from core, and no RDF/TTL parsing lives in the app.
- The assistant panel talks to `AletheiaAiClient` directly: `flow()` for the one-shot intent classification (it needs only the terminal output) and `flowStream()` for the fill, whose events drive the progress UI. No app-side AI adapter exists.
- `n3` stays an explicit dependency (and `@types/n3` a devDependency) because the SDK core declares `n3` as a peer for its SHACL validator.
- The AI assistant panel/wizard and the rental stage wizard stay local; the SDK ships no equivalent component.
- The header and sidebar stay bespoke (senior-audience chrome); the theme switcher, buttons and cards come from `-ui`. The SDK sidebar's `[sidebarFooter]` slot is the seam for adopting `aletheia-sidebar` later — it would let Homestia project its accent/language cluster into the SDK rail, at the cost of adopting the SDK's own nav chrome.
- Local spartan primitives are reduced to `libs/ui/utils` + `libs/ui/accordion`; the accordion is the only component with no SDK equivalent.
- The accent palettes remain a Homestia-owned CSS axis (`[data-theme]`, `accent.service.ts`) layered on top of any skin; `--primary`, `--primary-foreground` and `--ring` are the only tokens they set.
- The `homestia` skin is registered through `provideSkins([HOMESTIA_SKIN, ...SKINS])` and is first, so it is the default.
- Entity types, entity-info constants, `paths.ts` and `capabilities.ts` are generated by `@rennnyyy/aletheia-cli` from `model.json`; `codegen:check` is the drift gate and must be part of CI. ^consequences
