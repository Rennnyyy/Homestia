# Ownership Is a Server Gate, and the Host Provisions the Landlord

**Status**: accepted
**Type**: decision
**Supersedes**: none

## Statement
A property belongs to the landlord that created it, a room belongs to the landlord of the property it is part of, and a landlord belongs to the agent the platform infuses as `?agentIri`. The rule is enforced by the Aletheia aspect layer, not by a page: the **property** and **room** query aspects carry an ownership `FilterWhere` (the read gate, stated as the ALLOW clause the access gate expects), the **landlord** query aspect carries the strict form of the same clause (an unknown agent is answered with nothing), and the **property**, **room** and **landlord** operation aspects carry an ownership `ContextWhere` (the write gate, stated as the DENIAL clause the context pass expects). A property names its landlord through its own owning predicate (`Property.Landlord`, `landlord`), and `Landlord.Properties` is the read-only inverse. The **host** gives every identified caller its own landlord (`LandlordSyncMiddleware`, the domain counterpart of the SDK's agent projection) and the **page** only binds what the landlord collection hands back. ^statement

## Rationale
Four forces decide the shape.

**The gate must be server-side.** A page that stops binding a landlord still looks right, and only the server can refuse a read a page never made — so the proof of the feature is a second agent's API call, not a screen.

**Polarity is a trap.** The read gate wraps a filter in `SELECT ?granted … BIND(true AS ?granted)` and every returned row is a GRANT, while the write gate turns every returned row into a VIOLATION. One sentence about ownership cannot be written once and reused; both clauses exist, each asserting the same fact the other negates, and each has a test that fails if it were inverted.

**Direction is the other trap.** The context pass runs *before* the operation's own triples land, so a room created inside a property created by the same aggregate save can only be judged if the property already carries its landlord — which is why the property owns the link rather than the landlord's collection, and why the write gate skips a record that does not exist yet (a create is not judged by what it will hold; it is made reachable by the caller that creates it).

**The client cannot name its own agent.** The agent IRI is the property-based encoding of a token the browser never sees, so a page cannot find-or-create its landlord — it could not fill in the one field that makes the landlord *its own*. Left to the client, a caller with no landlord could not create one, and — because the write gate judges a property by the landlord it carries — could not create a property either. Provisioning therefore happens where the agent is known: the host mirrors the acting agent into the domain record ownership starts at, and the client's whole job becomes "ask the collection for my landlord and bind it". That is also why no identity endpoint is needed: the landlord collection *is* the identity query, which is why its gate is strict (a permissive "no agent ⇒ everything" answer would hand an anonymous caller the first landlord in the store — somebody else's — and the page would bind it).

## Consequences
- `Homestia/src/Aspects/OwnershipRules.cs` holds the one sentence, the predicate IRIs (resolved from the entities, never hand-written) and the clause builders — `AllowFilter` (permissive default, for the collection gates), `RequireOwnFilter` (the identity query) and `DenyViolation` (the write gate) — so a read and a write cannot drift apart.
- The aspect code lives in its own slice: `Homestia/src/Aspects/` (`AspectFields`, `OperationAspects`, `QueryAspects`, `ViewAspects`, `OwnershipRules`) next to `Capabilities`, `Entities`, `Program` and `Web`. The Program registers what the slice builds; nothing in the slice depends on the host. `shape-bindings.spec.ts` reads these files, so their path is part of the contract it checks.
- `Property.Landlord` (`[Owning("landlord")]`) is the owning side; `Landlord.Properties` is `[Inverse(nameof(Property.Landlord), "owns")]`. A write shape may not name an inverse predicate, so the landlord's writable surface is `agent` (required) + `landlordType`.
- `Landlord.Agent` points at `Aletheia.Sdk.Authorization.Entity.Agent` — the type `?agentIri` resolves to. Homestia's own `Aletheia.Authentication.Agent` stub is **gone**: it was a placeholder for the authentication layer the platform now provides, and `Tenant` no longer inherits it.
- `Tenant` is standalone: `[Entity(Path = "tenants", PredicatePath = "tenant")]` with its own `[Identity(Random)]` and its own `displayName`. Its operation route is still `tenants`, so no page changes — but its instance IRIs move from `{BaseIri}/agents/{id}` to `{BaseIri}/tenants/{id}`, its type from `types/agents/Tenant` to `types/tenants`, and its predicates from `/predicates/agents/*` to `/predicates/tenant/*`. **Records created before this change stay in the store but fall out of the tenant list** (the list scans the type); a store created fresh, or tenants re-created, is unaffected. Worth a migration only if a populated environment must keep them.
- `AspectFields.TargetSuffixOf` has no tenant exception any more: every shape targets its entity's concrete type segment (ADR-0016), which is what the stored records carry.
- The app-scope definition feed (`AddEntityEntity`) registers `Homestia.Entities` only. The authorization Agent is therefore **not** in `model.json`, and the generated `Landlords` interface has no `agent` member — the relation is dropped because the projection cannot describe its target. The page never reads that member: the gate already answered "which landlord is mine". (Registering the authorization assembly as well BREAKS codegen: the SDK's projection emits that assembly's `AgentIri`/`RoleIri` string-references twice, as a property and as a relation.)
- The identity is projected into the store by the SDK's `UseAgentSync()` (`Aletheia.Sdk.Authorization.Http`): whoever the ambient identity middleware established — a verified Authentik forward-auth JWT in a deployment, a bearer token or a DECLARED agent locally (the SDK's development simulation, `AddAgentSimulation()` / `UseAgentSimulation()`) — becomes an `Agent` on their first request. `LandlordSyncMiddleware` then mirrors that agent into a landlord. Both are best-effort and never block the request, and both are stamped once per agent per UTC day.
- Homestia's own copy of the agent projection (`src/Program/AgentSyncMiddleware.cs`) is **gone**: the pinned SDK release `0.9.7-rc.3abb53c` carries the promoted `UseAgentSync()`, so the host calls the SDK's — and the local copy had to be deleted rather than kept, because two `UseAgentSync()` extensions in one compilation unit resolve to neither. The same release supplies the development agent switch (`provideAgentSimulation()` + `agentSimulationInterceptor` + `aletheia-agent-simulation-switcher`), which replaced Homestia's hand-rolled `?as=<token>` bearer switch (`src/app/core/identity/dev-identity.ts`, deleted).
- A property saved without a landlord is unreachable by everyone, including its author: the shape admits the field but does not require it (a required field would refuse an update that legitimately does not re-send it), so the binding is the page's duty. `e2e/zz-ownership.spec.ts` proves the binding, the stranger's refusal (property *and* landlord), the reuse of one landlord across properties, and that an anonymous caller binds nothing; `Program.Tests` proves the polarity and the predicates each clause names. ^consequences
